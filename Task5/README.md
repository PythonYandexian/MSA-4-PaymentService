# Task 5. Тест-кейсы: интеграционные и end-to-end

## Принцип тестирования

Тесты проверяют **внешнее поведение саги**, а не детали реализации: наблюдаемый результат — терминальное состояние процесса, изменение баланса, отправленное уведомление или появление задачи в Tasklist — а не факт вызова конкретного метода воркера. Единственный шов — Camunda REST API / external task client на уровне процесса: тест запускает `process instance` с контролируемым исходом mock-проверок и проверяет, в каком состоянии и с какими переменными процесс завершился. Юнит-тесты отдельных воркеров не предусмотрены — они проверяли бы реализацию, а не поведение саги.

**Прообраз (prior art).** Компания уже использует Testcontainers для лёгкого воспроизводимого окружения (см. стек в описании задания) — интеграционные и e2e-тесты поднимают Camunda + PostgreSQL + Redis через Testcontainers, а не мокают движок. Внешние провайдеры (AML/GeoRisk) поднимаются как мок-сервис с управляемым исходом (allow/deny/manual review), чтобы детерминированно воспроизводить каждую ветку из таблицы ниже.

**Компоненты в таблице** — это участвующие в кейсе сервисы/модули системы (Payment Service, FraudCheck, внешние провайдеры, Camunda, Redis, Tasklist), а не классы кода.

## Таблица тест-кейсов

| Название | Тип | Компоненты | Предусловия |
|---|---|---|---|
| Успешный сквозной платёж | e2e | Payment Service (оркестратор), FraudCheck (внутренние правила), AML/GeoRisk (внешние проверки), Notification | У клиента достаточно средств; все проверки возвращают `ALLOW` |
| Отказ антифрода с автоматическим возвратом | e2e | Оркестратор, FraudCheck, AML/GeoRisk, Notification, Security | Хотя бы одна из проверок возвращает `DENY`; средства уже списаны в рамках саги |
| Ручная проверка → оператор разрешает транзакцию | e2e | Оркестратор, Tasklist UI, FraudCheck | Все проверки вернули `MANUAL_REVIEW`; оператор доступен и отвечает в пределах 20-минутного SLA |
| Ручная проверка → оператор отклоняет транзакцию | e2e | Оркестратор, Tasklist UI, FraudCheck, Notification, Security | Аналогично предыдущему, оператор выбирает запрет |
| Срабатывание cut-off по истечении 20 минут | e2e | Оркестратор (движок таймеров) | Ручная проверка ожидает решения; оператор не отвечает до истечения окна |
| Сбой перевода контрагенту (после pivot-точки) | integration | Оркестратор, шаг `TRANSFER_TO_MERCHANT` | Антифрод вернул `ALLOW`; вызов перевода завершается ошибкой или таймаутом у контрагента |
| Отказ списания из-за недостатка средств | integration | Оркестратор, шаг `DEBIT_ACCOUNT` | Баланс клиента меньше суммы платежа |
| Идемпотентность повторного вызова внешней проверки | integration | Redis (кэш), AML/GeoRisk mock | Проверка для `transactionId` уже выполнена и закэширована; топик повторно взят в обработку (например, после разрыва соединения до подтверждения движку) |
| Идемпотентность повторного выполнения `DEBIT_ACCOUNT` | integration | Оркестратор, доменное хранилище платежей | Списание уже выполнено, но воркер не успел отчитаться до истечения lock duration — движок повторно назначает ту же задачу |
| Параллельное выполнение AML и GeoRisk укладывается в SLA | integration | Оркестратор, AML/GeoRisk mock | Обе внешние проверки отвечают с задержкой; суммарное время меньше, чем при последовательном вызове |
| Недоступность внешнего провайдера с восстановлением через retry | integration | Оркестратор, AML/GeoRisk mock | Провайдер временно возвращает ошибку/таймаут на первый вызов, затем отвечает штатно |
| Компенсации выполняются в обратном порядке | integration | Оркестратор, `REFUND_TO_CUSTOMER`, `CANCEL_PAYMENT` | Сага скомпенсирована после `DENY` или сбоя перевода; проверяется порядок вызовов (сначала откат более позднего шага) |
| Повторная инициация платежа с тем же идемпотентным ключом | integration | Оркестратор, шаг `CREATE_PAYMENT` | Клиент повторно отправляет тот же запрос на оплату (например, после сетевого таймаута) с тем же `paymentId` |
| `NOTIFY_SECURITY` вызывается ровно один раз на платёж | integration | Оркестратор, Security-уведомление | Сага прошла по ветке `DENY`; проверяется отсутствие дублирующих уведомлений при retry шага |
| Деньги не зависают при сбое на любом этапе после списания | e2e | Оркестратор, вся цепочка компенсации | Симулируется сбой на случайном шаге после `DEBIT_ACCOUNT`; итоговое состояние — `COMPLETED` либо `REFUNDED`, промежуточных зависаний нет |
